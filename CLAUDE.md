# CLAUDE.md

## What this project is

A gallery-centric actuarial reserving package: Bayesian MCMC and neural network loss reserving methods with mandatory evaluation, model stacking, and a long-format triangle data layer backed by duckdb and polars. Designed as a companion/extension to `chainladder-python`, not a fork of it.

Name: **ibnr**, published on PyPI since 2026-07-23 (`uv add ibnr`). The GitHub repo and the local checkout are both `ibnr` too, so package, repo and directory all agree. License: MPL-2.0 (deliberately matches chainladder).

## Dev commands

```sh
uv sync                                   # core + dev deps (incl. polars, so both backends are tested)
uv sync --extra bayesian                  # + cmdstanpy/numpyro/pymc/arviz/bayesblend (works on py3.12)
uv run pytest                             # fast suite (slow excluded via addopts); transforms run on BOTH backends
uv run pytest -m slow                     # cmdstan tests (compile + sample); needs cmdstan installed
uv run pytest "tests/test_transforms.py::test_as_of[polars]"   # single test, one backend
uv run ruff check . && uv run ruff format .                    # format also rewrites python blocks in *.md
uv run python scripts/lint_md_snippets.py                      # lint those blocks (ruff check ignores markdown)

```

Markers: `tieout` (chainladder comparisons), `mart` (needs the local Schedule P gold mart; auto-skips when absent), `parity`, `slow` (cmdstan; excluded by default via addopts), `network` (really talks to the internet; also excluded by default - run with `uv run pytest -m network`).

## Core design decisions - do not relitigate without asking

1. **Long-format 2D triangles only.** No 4D arrays. A triangle is a tidy table: `origin_period, dev_lag, eval_date, field, value` + arbitrary segment columns (lob, company, ...). `eval_date` is a first-class stored column, not derived - all backtesting slices on it. Each triangle carries metadata: grain, cumulative/incremental flag, units. Reference design: Ledger Investing's `bermuda`.
2. **ibis is the dataframe frontend.** Both duckdb and polars backends are supported - no debate, both. Transformations (incr↔cum via window functions, grain changes, pivots, `as_of()` slicing) are written once in ibis. The transformation test suite runs against BOTH backends; ibis's polars backend has weaker window-function coverage, so expect and document gaps. **Amended 2026-07-23 (0.4.0), at Ethan's request:** *supported* is not *installed*. Only duckdb ships in the core dependency; polars moved to the `ibnr[polars]` extra because its runtime is ~176 MB (35% of the install) that a duckdb-only user never executes - it was blocking deployment of an Azure Function that imports ibnr. The dev group still installs polars, so the dual-backend test matrix is unchanged and this decision keeps its teeth. duckdb stays the default backend.
3. **The Stan `data` block is the data contract.** `kernels/contract.py` maps Triangle → standardized dict. NumPyro and PyMC implementations consume the identical dict. Never let a backend grow its own data prep.
4. **`PredictiveDistribution` is the unifying output type** (`kernels/predictive.py`). Every gallery entry - Bayesian, NN, deterministic - must produce one. NN models require distributional heads (mixture/quantile heads or deep ensembles); point estimators cannot enter the gallery. Deterministic baselines (Mack, basic CL) are wrapped with bootstrap.
5. **Evaluation is a contract, not a feature.** `GalleryEntry` ABC requires `.fit()`, `.cohorts()`, `.predict()`, `.realized_ultimates()`, `.evaluate()`, `.card()`. An entry that fails the eval harness does not register. **Amended 2026-07-28 (0.5.0): the ABC gained a cohort vocabulary.** `cohorts()` (abstract) returns each cohort's FULL segment identity as the triangle carried it, in `predict()`'s target order; `cohort_index(segment)` is the one concrete resolver every entry uses, where `segment` is a FILTER on the fit's cohorts (any subset naming exactly one is accepted, naming none raises); and `predict`/`realized_ultimates`/`evaluate` all take the identical leading `segment: Mapping | None = None`. Before this the NN entries took a segment dict and the other ten took none, and `realized_ultimates` - implemented on all 15 - was not on the ABC at all, so a cross-model outcome table needed caller-side `family == "nn"` branching. `cohorts()` is deliberately NOT defaulted to `contract_["segment"]`: a pooled entry that forgot to override would get a plausible answer from a key that happens to exist. `config_class` (ClassVar) names the dataclass `fit(config=...)` takes, checked at registration in BOTH directions - missing when `fit` takes one, or declared when it does not. Eval algorithms (ELPD/LOO/WAIC, PIT calibration, stacking via `bayesblend`, ArviZ-based diagnostics) are implemented ONCE in `kernels/` - gallery entries call them, never reimplement.
6. **Eject-pattern codegen, not a formula DSL.** Every gallery model is literal, readable source: `model.stan`, `model_numpyro.py`, `model_pymc.py` side by side. Precedent: brms/bambi, but simpler. **`gallery.scaffold()` is PLANNED, not built** (no `gallery/scaffold.py`, nothing in `gallery.__all__`) - it is meant to copy an entry's source into the user's project for them to extend (copulas, priors, hyperparameters). The constraint it implies is already live and must be kept: each model directory has to stand alone, importable and readable without the rest of the package, so a future scaffold is a file copy. Several cards and model modules already say "for `gallery.scaffold()`"; read those as the standing requirement, not as a shipped API.
7. **Cross-backend parity is a feature.** `kernels/parity.py` validates that NumPyro/PyMC ports match the Stan reference posterior before any convergence/speed comparisons. Parameterization (centered vs non-centered, truncation handling, init strategy) is an explicit documented attribute of each model card. Stan implementations from the literature are ground truth.
8. **Small public API.** As built (checked 2026-07-29): `ibnr.__all__` is `Triangle`, `TriangleMeta`, `__version__`; `ibnr.gallery.__all__` is `SCORE_DIRECTION`, `Absence`, `CohortForecast`, `GalleryDiagonal`, `GalleryEntry`, `align_panel`, `fit`, `get`, `leaderboard`, `list`, `next_diagonal`, `stack`. **The rule the export set follows (added 2026-07-28, 0.5.0; second clause added 0.5.1):** a name is exported if a caller has to CONSTRUCT or CALL it to get from a fitted entry to a **published result - a board row or a one-year CDR** - `next_diagonal` (which cells), `CohortForecast` (one model's arrays at them), `Absence` (why an array is missing; `CohortForecast` refuses an absent array without one, so it is not optional), `align_panel` (the cross-model intersection), `leaderboard`, plus `SCORE_DIRECTION` because `leaderboard()` has no default sort and no `sort_by=`. **`GalleryDiagonal` (0.5.1) is the only name the second clause has admitted**, and it had to be exported rather than reached by name: `kernels.cdr.cdr_methods()` hands out `"mack"` and `"odp_bootstrap"` as strings, but this generator carries a *fitted entry* plus its held-out cells, which no string can, so without the export there is no short way to write it down. `tests/test_gallery.py` now splits `EXPECTED_EXPORTS` into kernels re-exports and `GALLERY_OWN_EXPORTS`; before that the identity test looped over kernels modules and passed **vacuously** for any name none of them had. Before that only `leaderboard` was exported, so the pipeline's last step was on the small public API and its first three were not (notebook 03's import block reaches three levels into `kernels` for them). Deliberately NOT exported: `ForecastPanel`/`HoldoutCells` (returned, never constructed), `logmeanexp`, `resolve_field`, `CAPABILITIES`, `ABSENCE_REASONS`, `index_into`, `CellIndex`, and `ScoresHeldout`/`PredictsHeldout` - a caller tests capability with `isinstance` and those names are how an ENTRY declares one, so they stay at `ibnr.gallery.entry`. Re-export direction is gallery -> kernels only; `kernels` never imports the gallery (subprocess-tested), which is what lets the harness's spawn-based workers import it alone. Two names from the original statement are NOT there and the difference is deliberate, not drift: **`gallery.evaluate()` does not exist and should not** - evaluation is per fitted entry (`entry.evaluate(observed, segment=None)`, decision 5's ABC method), because scoring needs the fit that produced the prediction, and the cross-model layer is `leaderboard`/`stack` over a shared panel. **`gallery.scaffold()` is planned** (decision 6). Two consumer-facing surprises worth knowing before changing this surface: `import ibnr; ibnr.gallery` is an `AttributeError` (a submodule is an attribute only once imported - use `from ibnr import gallery`), and `gallery.get(name)` returns the entry **class**, so the call is `gallery.get("mack")().fit(tri)`. Both are documented in the README.

## Tooling & conventions

* `src/` layout, `uv` for env + packaging, `ruff` for lint/format, `pytest`.
* **Lint, as of 2026-07-26: ruff >= 0.16, and the version lives in `uv.lock` only.** CI reads it from there rather than running `uvx ruff` (which floats to the newest release and can turn a green branch red on its own). The lint job runs three gates: `ruff check`, `ruff format --check`, and `scripts/lint_md_snippets.py`. The floor is 0.16 because that is the first release whose formatter reaches python code blocks inside markdown - README and model cards are now formatted like source (this cost the aligned trailing comments in the README samples). `ruff check`, by contrast, ignores markdown entirely with no setting to change that, so the script extracts each fenced `python` block and lints it under the project's own config, ignoring `F821`/`E402`/`I001` because those fire on the shape of an excerpt rather than a defect in it. It also rejects blocks that do not parse - the formatter passes those in silence, so nothing else catches a doc sample that is broken Python. Tests: `tests/test_markdown_snippets.py`, `tests/test_lint_pins.py`.
* Optional extras keep the core light: `[polars]` (the second ibis backend), `[interop]` (chainladder, bermuda-ledger, for the `to_*` converters), `[bayesian]` (cmdstanpy, numpyro, pymc, arviz, bayesblend), `[nn]` (torch), `[viz]` (altair, quarto tooling). Core deps ≈ ibis-framework[duckdb] + scipy (scipy added 2026-07-06 for the statistical family; deliberate exception to "ibis only"; polars split out 2026-07-23, see decision 2). Torch must never be imported at module level - `ibnr.gallery` imports (and nn entries register) without the `[nn]` extra; `tests/test_gallery.py` enforces this in a subprocess.
* **numpy 2 is the tested generation, and `[tool.uv] override-dependencies` is what buys it (2026-07-26, 0.5.0; do not relitigate).** The core floor stays `numpy>=1.26` and deliberately NOT `>=2`: that floor already resolves to numpy 2.x for a plain `pip install ibnr`, while raising it would make `pip install ibnr[interop]` and `ibnr[bayesian]` unsatisfiable - bermuda-ledger 2.3.0 and arviz 0.18.0 (pulled by bayesblend 0.0.8's `arviz>=0.18,<0.19`) are the newest releases of their projects and both cap numpy below 2. The numpy 1.26.4 that used to sit in `uv.lock` was a property of THIS repo, where every extra resolves alongside the core and drags those caps in - not of the published package. So the lock steps over them with `override-dependencies = ["numpy>=2,<2.5", "arviz>=0.23,<1", "matplotlib>=3.10"]`, each verified by running the suite, not by reading changelogs. Overrides are a uv concept and never reach the published metadata, which is exactly the point: dev and CI run the numpy a consumer already gets, without shipping metadata nobody can satisfy. Write the numpy entry as a FLOOR - the permissive `numpy>1.23.1,<2.5` changed nothing, because an override only widens what is allowed and uv then re-prefers the version already locked (1.26.4). `<2.5` is numba's real cap, inherited via chainladder -> sparse; drop it when numba supports 2.5.
* **The package caps at Python 3.12 - `requires-python = ">=3.11,<3.13"` - and that ONE line is the whole policy (Ethan's call 2026-07-28).** It is not a limit of the code: core, `[polars]`, `[nn]` and `[viz]` were measured resolving wheels-only on 3.11 through 3.14. The cap exists for `[bayesian]` and `[interop]`, which both transitively pin numpy<2 (arviz 0.18.0 via bayesblend 0.0.8; bermuda-ledger 2.3.0), and the newest numpy under 2 is 1.26.4, which has no cp313 wheel and does not build on 3.13 - no pin we could write makes those extras work there. Metadata cannot express "3.11-3.14 unless you asked for `[interop]`", so the package claims one range for everything it ships and 3.13 gets the standard "requires a different Python" refusal (measured on a clean 3.13 venv: pip prints `Package 'ibnr' requires a different Python: 3.13.13 not in '<3.13,>=3.11'`). One measured caveat worth knowing before trusting a local test of this: **uv 0.11.7 does NOT enforce `Requires-Python` for a wheel installed from a path or `--find-links`** - `uv pip install`, `uv pip compile --python-version 3.13` and even `uv add` into a project declaring `requires-python = ">=3.13"` all accepted the 0.5.0 wheel on 3.13/3.14. pip, which reads the wheel's own METADATA, refuses. Test this cap with pip, or against the published index, never with `uv` and a local file. Do NOT try to buy 3.13 back with per-extra markers: a marker alone is a silent no-op (the extra resolves WITHOUT bayesblend/bermuda and the user meets `ModuleNotFoundError` at import), and an unmarked dependency only errors under `--only-binary` - a plain `pip install`, with sdists allowed, resolves to unbuildable numpy 1.26.4 sources and dies minutes later inside cc. Both measured. Also rejected, after being built: gating the extras on a deliberately unregistered sentinel package name, which produces a clean self-describing error but only while nobody else uploads that name. Revisit the cap when bayesblend drops `arviz<0.19` and bermuda drops `numpy<2`.
* **`ibis-framework>=9.5,<13`, in the core dependency and the `[polars]` extra alike.** 12.0.0 is what `uv.lock` resolves and what every CI leg runs. ibis has broken this repo across majors before - the polars backend's total absence of window functions (Gotchas) is an ibis 10.x fact `transforms.py` is written around - so a major bump is a deliberate change with the dual-backend suite re-run, never something a fresh resolve does silently.
* Test markers: `-m tieout` (results match an external reference: chainladder-python on raa/clrd, or R ChainLadder's published `CDR()` output on MW2014), `-m parity` (cross-backend posterior matching), `-m slow` (cmdstan compilation; separate CI job).
* CI matrix runs core and each extra in isolation to catch hidden imports.
* Interop is sacred: `Triangle.from_chainladder/to_chainladder`, `from_bermuda/to_bermuda` must round-trip losslessly.

## Related project (data source)

`https://github.com/EKtheSage/cas-schedule-p-data-model` (local checkout at `C:\Users\EthanKang\Projects\cas-schedule-p-data-model`) - Ethan's CAS Schedule P database (Data Vault warehouse, versioned gold publishes). **The repo is PUBLIC.** **Default consumption is via GitHub releases**: each gold promote is an immutable release tagged with its publish_id; `load_schedule_p()` with no source resolves `github://EKtheSage/cas-schedule-p-data-model@latest`, caches to `~/.cache/ibnr` (or `IBNR_CACHE_DIR`), sha256-verifies against the release manifest. Local dev works the same way - the warehouse checkout is only an override (`IBNR_SCHEDULE_P_WAREHOUSE` or explicit path), mainly for producer-side pipeline work. Experiment runs should pin a concrete `@publish_id`; the harness scripts stamp it into every results CSV.

**Transport (amended 2026-08-04): anonymous HTTPS is the primary path and `gh` is only a fallback.** Because the repo is public, `data/schedule_p.py` fetches with stdlib `urllib` - `GET https://api.github.com/repos/<repo>/releases/latest` to resolve `@latest`, and a streamed `GET https://github.com/<repo>/releases/download/<tag>/<asset>` for each asset (60 s timeout, `User-Agent` header - GitHub rejects requests without one - temp file then atomic rename). The `gh` CLI is tried ONLY when the anonymous request raises, which in practice means the API's 60-requests/hour/IP unauthenticated rate limit (and only `@latest` resolution touches the API at all) or a repo that has gone private again. When both routes fail the error names both and the distinct fix for each - pin a publish_id vs `gh auth login` - because sending someone to `gh auth login` for what is usually a proxy wastes an afternoon. So a fresh clone with no GitHub tooling now works, and `gh` is no longer a dependency of anything. Everything downstream is unchanged: same cache layout, same sha256-against-manifest verification, same `pinned_source()` semantics for the harness workers. The fallback triggers on a WIDE except - `(OSError, http.client.HTTPException, ValueError)`, plus `RuntimeError` on the tag path - because the realistic failures are not `URLError`: a connection reset after a 200 is `OSError`, an `IncompleteRead` is `HTTPException`, and a proxy's HTML error page is json's `ValueError`; all must reach gh rather than surface raw (review finding, with a pre-fix-failing test for the reset and the garbage-payload cases). Both gh subprocess calls carry timeouts (60 s tag / 600 s download). `tests/test_schedule_p_github.py` covers route selection by patching `urllib`/`subprocess`/`shutil.which` rather than the dispatcher (patching the dispatcher makes every such test pass whichever route the code took); the transport tests cannot pass against the pre-change gh-only module - rerun there, they error at the urllib patch point, since the old module never imports urllib - so none of them passes vacuously. One real-network smoke test carries the new **`network`** marker, deselected by default via `addopts` (`-m "not slow and not network"`) exactly as `slow` is - a box with working DNS is not consent to hit api.github.com on every `uv run pytest` - and it stubs `shutil.which` to `None` so it tests anonymous access rather than the developer's `gh auth login`. Known and accepted: `@latest` takes whatever `releases/latest` returns, so if the data repo ever publishes a package-style `v*` release the resolution would pick it; that fails loudly (no `manifest.json`, or a publish_id/tag mismatch) rather than silently, so no filter was added.

**The Meyers company screen lives in the data's own package, not in this repo (2026-08-04).** `cas-schedule-p` is on PyPI (2026.6.13, bundling data publish 20260613_041006) and this repo's dev group depends on it. `scripts/meyers_validation.py` no longer DEFINES the screen; it imports all nine names (`MEYERS_LINES`, `CV1_LIMITS`, `CV2_LIMITS`, `EXCLUDED_GROUPS`, `TRAIN_AYS`, `MIN_PREMIUM`, `MIN_LOSS`, `AS_OF`, `select_companies`) from `cas_schedule_p.screens` and re-exports them, so every existing `from meyers_validation import ...` in `compare_gallery.py`, `parity_gallery.py`, `heldout_leaderboard.py` and notebook 03 keeps working unchanged. The screen constants and SQL were verified identical to the deleted literals before deleting them (all eight constants equal; selected company lists identical per line - the only difference is a ~1e-16 wobble in the reported `cv1`/`cv2`, which is duckdb's own run-to-run float nondeterminism, reproduced by running the *same* function twice). **Why this is a stronger no-drift guarantee than the old "there is one copy, import the script":** that copy lived in a different repository from the mart it queries, so nothing tied a screen constant to the data version it screens, and a downstream user of the published mart had no way to get the screen at all. Now the constants, the SQL and the parquet are one release artifact with one version number, and a published cohort is reproducible from two pins - the package version and the mart's publish_id - rather than from a git commit of a script. **Load-bearing call-site rule:** every caller keeps passing its own resolved `mart_path` explicitly. `cas_schedule_p.screens.select_companies` defaults `mart_path=None`, meaning the mart bundled in the wheel - a fixed vintage, right for a caller who wants exactly that, wrong for a retrospective, which must screen on the publish it FITS or the cohort comes from one dataset and the triangles from another (and `--warehouse` would silently stop reaching the screen). `pip install cas-schedule-p` is also the zero-setup route for anyone who just wants the mart: the wheel carries it, no download and no GitHub access at all.

**Amended 2026-09-04 (unreleased): the compute image installs it, pinned, and that is now tested.** The package is deliberately not a dependency of the wheel, so the Dockerfile's `.[bayesian]` install never brought it, and the image's own `CMD` (`python scripts/meyers_validation.py --help`) would stop at `ModuleNotFoundError` before printing a line. Nobody built the image to find that out, here or in CI: there is no Docker on the dev box, so the command was run instead with `cas_schedule_p` absent from the import path. The Dockerfile now installs `cas-schedule-p==2026.6.13` on the same `pip install` line, and `tests/test_compute_image.py` holds that pin equal to `uv.lock`'s and starts each script the image promises inside a subprocess that refuses every module outside what those install lines put there. Two limits of that subprocess, both written into the file: it is one-directional, so a package the image HAS and a lean CI leg does not is reported as the leg's gap rather than the Dockerfile's (sending someone to install what is already installed wastes the afternoon the `gh auth login` message above wastes), and the set of distributions it computes comes from locally installed metadata, so it can be smaller than the image's on a leg that syncs no extras. Neither costs anything today: no script the image promises imports such a package, and the answer is identical on all seven CI legs.

**Out of band (2026-07-27; asked for directly): the wire format.** `kernels/codec.py` - `to_arrow`/`from_arrow`/`to_summary`/`peek_kind`, plus thin `to_arrow`/`from_arrow` methods on `PredictiveDistribution`, `Triangle`, `MackFit`, `MackFitPanel`, `CDRResult`, `ForecastPanel` and any DataFrame. Until now `PredictiveDistribution` had no serialization at all, so nothing this package produces could cross a process or network boundary. One Arrow IPC stream per artifact, **uncompressed by default**, with the kind, a JSON header and nested streams for auxiliary frames/arrays carried in the schema metadata. Measured on the payload an API actually returns (10 targets x 10,000 draws, 800,000 B raw), median of 50 encodes after 5 warmups on the dev box (Intel Core Ultra 9 285H / Windows 11 / pyarrow 24): Arrow uncompressed 802,888 B / ~0.5 ms encode, Arrow lz4 803,320 B / ~0.9 ms, Arrow zstd 742,432 B / ~1.4 ms, parquet defaults 978,363 B / ~7 ms (BIGGER - it attempts dictionary encoding on doubles that are all distinct), JSON 1,952,983 B / ~39 ms, summary JSON 3,571 B. **The sizes are exact and reproduce byte for byte; the times are one significant figure and no more** - the same 50-encode median moved 0.38 to 0.64 ms across sessions, so the ratios are the finding and the milliseconds are context. The published 0.10 ms was a single-run figure and is superseded. So compression is a knob and never a default (7.5% of the size for ~3x the CPU; lz4 comes out larger than both the uncompressed envelope and the raw draws), parquet is the right codec for a bulk triangle export and the wrong one for draws, and JSON carries a SUMMARY - one-way, with no `from_summary`, because a summary is not a distribution (decision 4). Draws are lossless bit for bit and the tests compare `samples.view(np.uint8)`: float32 costs 6e-8 relative error (the float32 rounding bound, 2**-24) and 10x thinning moves the 99.5th percentile a median 2.2% over 200 seeds against 0.7% for the median quantile - the tail degrades ~3x faster than the middle - and both pass an `allclose` assertion cleanly. `pyarrow>=15` moved from the dev group into the core dependencies - it was already there transitively via `ibis-framework[duckdb]` (`pyarrow>=10.0.1`), and codec.py imports it directly. Two things Arrow does NOT round-trip on its own and `_TAGGED_COLUMNS` handles: object columns of tuples (`ForecastPanel.cells.key`/`cohort` - a list column decodes to an unhashable ndarray, so the panel raises on first groupby rather than at decode) and object columns mixing values with `pd.NA` (`pointwise.n_draws_density`, `by_cohort.elpd` - Arrow types them int64/double-with-nulls and pandas hands back float64 NaN, silently converting "no score" into "not a number", which is exactly the distinction milestone 6 rests on). Those columns are tagged value by value; an unknown type is refused by name rather than coerced to its `repr`. Triangle decode goes back through `io.from_long`, so there is no second ingestion path and the null-segment guard fires on the wire boundary too; `backend` is a decode-time argument and is never encoded. `tests/test_codec.py` is mutation-verified - 13 deliberate breakages (float32 draws, 10x thinning, trusting Arrow with every object column, deriving `n_obs` from `n_pos`, dropping the panel's `errors`, accepting any codec version, letting NaN escape the summary, defaulting the triangle metadata on decode, float64-ing the board, dropping a fingerprint, dropping `compression` in one encoder, ignoring `backend=` on triangle decode, ignoring `quantiles=` in the summary), all caught. **The compression one was found by review, not by the tests, and it is the repo's named inert-parameter bug class:** `_encode_triangle` took `compression` and never forwarded it to `_pack`, so `Triangle.to_arrow(compression=...)` was a no-op and even `compression="not_a_codec"` was accepted silently - plain, lz4 and zstd all came out byte-identical at 1,608 B. The lesson is the one already in memory: a test of the decoded ANSWER can never see an inert argument, because the round trip is perfect either way. The compression tests are now parametrized over `codec._ENCODERS` itself, so a kind cannot join the registry without joining the parametrization. Not yet done: the HTTP layer itself (content negotiation on `Accept`, `X-Ibnr-Kind`, 202 + job handle for a 200 s fit) - the codec is the seam it will sit on.

**Codec hardening (2026-07-28), from an external review of the above.** Five defects, all of the same family as the compression one - the round trip is perfect and the thing that is wrong is not in the answer. (1) **The typed `from_arrow` classmethods did not check the kind.** They delegate to a dispatcher that routes on the payload's own `ibnr.kind`, so `PredictiveDistribution.from_arrow(triangle_bytes)` returned a **Triangle** - a real, correctly decoded artifact of the wrong class, failing later and somewhere else. `from_arrow` gained `expect=`, and all six typed entry points plus every nested `MackFitPanel` child pass it; the test decodes the wrong kind through each entry point, parametrized over `_DECODERS` so a new kind cannot skip it. (2) **The DataFrame index was not carried through the tagged-column machinery** - only the data columns were. An `Int64` index of `[3, pd.NA]` came back float64 `[3.0, nan]`, the same missing-versus-value collapse milestone 6 rests on, one axis over; and an object index of tuples raised inside `pa.Table.from_pandas` outright, so a frame keyed by cohort could not be sent at all. Every non-range index now travels as ordinary columns (placeholder labels, suffixed until free) and a RangeIndex as its start/stop/step, so the empty-body kinds stay empty. Two traps found while building it, both measured: `pd.Index(series, name=None)` **inherits the Series' name**, so an unnamed index came back named after the placeholder column (caught by the mutation pass, not by the first round of tests, which were all named); and `tupleize_cols=False` is **inert** against a Series or ndarray input on pandas 2.3.3 - only a *list* of tuples is tupleized - so it is kept as a guard against the input type changing and is documented as inert today rather than presented as live. Nothing this package builds is affected: every frame in `ForecastPanel`, `MackFitPanel`, `MackFit.summary()`, `leaderboard()` and `PredictiveDistribution.targets` carries a plain RangeIndex (checked), so the fix is for the `DataFrame` kind - a caller's own frame. (3) `MackFit.cum` was rebuilt at a hardcoded float64 while every other array on the class records its dtype; it now records `cum_dtype`. (4) `to_summary` **skipped quantile validation when there were no draws** - the zero-draw branch never reaches `np.quantile` - so the same call was accepted or refused depending on the data rather than on the request; the grid is checked in one place for both. (5) `_untag` ended in a bare `return value`, so an unknown tag came back as its JSON shape (a list where a tuple was) instead of being refused by name; `_TAG_KINDS` now pins the encoder's and decoder's tables together. Mutation-verified: 14 deliberate breakages, all caught (dropping `expect` in two typed decoders and in the dispatcher, leaving `expect` itself unchecked, unchecked nested children, index left to pyarrow, a non-unique placeholder, index levels coerced through object, the unnamed-index name, dropped MultiIndex names, float64 `cum`, both halves of the quantile check, the tag fall-through).

**Rejected after measuring, same review: deferring `kernels/codec.py` behind a PEP 562 `__getattr__`.** The reviewer's premise was that the eager `from ibnr.kernels.codec import ...` in `kernels/__init__.py` charges every `from ibnr import gallery` ~3.7 s of pyarrow import. It does not, and the reason is one line of pandas: `pandas/compat/pyarrow.py` runs a bare `import pyarrow` whenever pyarrow is installed, which it always is because the codec requires it - so **pyarrow is in `sys.modules` before ibnr's first line either way**, and 3.7 s is simply what `-X importtime` reports as `ibnr.gallery`'s own cumulative total. Built the lazy version and measured it interleaved (11 alternating reps per arm, warm bytecode, fresh interpreter each rep): `from ibnr import gallery` **eager 3.05 s median vs lazy 3.20 s**, spread 2.8-3.5 s, i.e. no difference; the lazy arm removes exactly **one** module from a 1,098-module process, and `scipy.special` - the other heavy import on that path - arrives via `kernels.densities` regardless. So `kernels/__init__.py` stays plain, with the measurement in its docstring, and `tests/test_import_purity.py::test_the_wire_format_is_not_what_a_public_import_pays_for` is a tripwire on the **premise**: it goes red if pandas ever stops importing pyarrow, which is when the deferral would start to pay. ## Gotchas

* ibis polars backend (ibis 10.x): **no window-function support at all** (`OperationNotDefinedError` for any `WindowFunction`), no `ScalarSubquery` either. Transforms use equi-join + group-by formulations instead (see `triangle/transforms.py`). Also: after `cross_join`, mutate derived expressions into real columns *before* filtering on them, or polars loses the joined column (`ColumnNotFoundError: 1__anchor`).
* chainladder semantics worth remembering (all encoded in the tieout tests):
  * valuation timestamps are end-of-day, so `tri[tri.valuation <= "1985-12-31"]` *excludes* the 1985 diagonal; use `< "1986"`.
  * triangle arithmetic treats missing cells as zero inside the observed region, so `cum_to_incr` fabricates increments at cells absent from the source and stores zero increments as NaN. Our long format means absent = unobserved, zero = explicit; we deliberately do NOT densify (it would fabricate data on `as_of` slices).
  * `grain('OYDY')` anchors dev buckets to the latest diagonal (ages 3, 15, 27... when the latest valuation is Q1). `change_dev_grain` matches this.
* bermuda's `Cell.dev_lag` measures from period *end* (first diagonal = 0); ours is months from origin *start* (first diagonal = 12). `from_bermuda` recomputes; never copy bermuda's dev_lag.
* **pytensor 2.31.7 cannot run on numpy 2.4+**, so the numpy-2 move needed a pymc upgrade and not just an override: pytensor unpacks `numpy.einsum_path`'s result as a 5-tuple, numpy 2.4 returns 3, and every LKJ-based compartmental test dies on "not enough values to unpack". pymc 5.28.5 / pytensor 2.38.3 fix it and are what `uv.lock` carries. Check this before pinning pymc back.
* "Same model" across PPLs is only same if parameterization is held constant - otherwise convergence comparisons measure implementation accidents.
* Schedule P triangles are small; NN overfitting is the central risk. All NN training validates across many company×LOB triangles, never one.
* Windows dev machine: cmdstanpy needs a working toolchain (RTools/MSVC); keep cmdstan-dependent tests behind `-m slow` and runnable on CI Linux.
* Never name modules shadowing deps (`altair_.py` not `altair.py`).
* **A missing outcome gets no percentile, not the 0th** (fixed 2026-09-04, `kernels/predictive.py::cdf`). Every comparison against NaN is False, so counting the draws at or below the outcome returned exactly 0.0 for a target with no outcome: the lowest percentile there is, which the uniformity test reads as the worst possible over-prediction, and which nothing downstream could tell apart from a genuine outcome below every draw. `cdf` now returns NaN where the outcome is missing or any draw at that target is missing, per target. Keep the two halves of the "the neighbours already answered NaN" claim apart, because they are not the same claim: `kernels.scores.crps` already answered NaN for a missing OUTCOME, while `mean`, `std` and `crps` all already answered NaN for a missing DRAW. `mean` and `std` take no outcome, so they are perfectly finite for a target that has none. Infinite outcomes and infinite draws are NOT masked, and `cdf([-inf]) == 0.0` is pinned by a test, because that verdict is what keeps a missing outcome distinguishable from an over-prediction. The missing-outcome half is latent on the Schedule P mart, which carries an outcome for every scored origin, and live on any backtest whose cutoff leaves an origin short of the fit's final development lag, the case `gallery/deterministic/mack` documents by name. **The missing-draw half is not latent: it moves one published number.** One never-converged fit in `analysis/results/compartmental_validation_lognormal.csv` (other_liability, company 16373, R-hat 1.25, bulk ESS 12) has missing draws, hence a blank estimate and a percentile of 0.0; dropping it takes other_liability from D = 20.2 (rejects) to 18.6 (passes, n = 49) and the combined figure from 16.2 to 15.9 (still rejects, n = 199). Those are recomputed from the stored percentiles, not re-sampled, and the compartmental card carries the note.
* The Schedule P mart carries accident years beyond the Meyers study window (1988-2007, not just 1988-1997). Any outcome/aggregate computed from the full triangle must restrict to the origins present in the as_of training slice, or it silently includes post-study accident years (bit `scripts/compare_gallery.py::point_context` once - 2.4x inflated "outcomes").
* **A held-out draw must declare its scale, exactly as a density declares its measure** (`PredictsHeldout.heldout_draw_scale`, one of `cumulative`/`incremental`). Three of the five Bayesian entries model increments while the Schedule P triangles are cumulative, so undeclared increment draws scored against `HoldoutCells.values` are wrong by the whole training-diagonal anchor - measured on a synthetic cell with anchor 1000: CRPS 996 where the truth is 3.4, both finite, both smooth. The conversion (`+ prev_value`, which is training data, so no leakage and the same fact that makes the increment/cumulative Jacobian 1) lives in the base class where an entry cannot skip it. What makes cross-scale comparison legitimate at all is that **CRPS is translation-equivariant** - `CRPS(F+c, y+c) == CRPS(F, y)`, verified to 5.5e-12 - so once each entry is on its triangle's basis the numbers are comparable.
* **Two vocabularies are both spelled "measure".** `HoldoutCells.measure` is the TRIANGLE's basis (`cumulative`/`incremental`); `densities.MEASURES` is the DENSITY's scale (`amount`/`log_amount`/`loss_ratio`). `forecast.py` carries the first and never the second, because `log_lik_at` guarantees everything reaching it is already on Lebesgue-on-amount - a field with exactly one legal value is a knob that cannot be turned.
* **`scipy.special.logsumexp`, never a hand-rolled max shift.** The textbook `m + log(sum(exp(x - m)))` returns **NaN** when `m` is `-inf` (i.e. when every draw gives the outcome zero density), with only a RuntimeWarning - and pandas then silently SKIPS that cell, so the model scores on fewer cells than everyone else. scipy returns `-inf`, which is the correct verdict. Measured in this environment.
* **Stacking's numerical boundary is the Jacobian's reciprocal overflowing, not `exp` underflowing, and bayesblend hands back an unfitted vector when it hits it** (fixed 2026-09-04, `kernels/stacking.py`). `MleStacking` exponentiates the pointwise ELPD and hands SLSQP the Jacobian `1 / (Y @ w)`. The limit is that reciprocal overflowing once `Y @ w` falls below `1 / DBL_MAX` (about 5.6e-309, log about -709.78), NOT `exp` underflowing to zero, which takes until about -746. Where that lands in the log densities depends on the weights and on the spread between members, because the mixture sits below its largest term: on sixteen board-like cells with two members three nats apart it is reached between -709.0 and -709.4 (measured: the fit at -709.0 is correct, the same fit at -709.4 is not, and the objective it reports is still finite). On failure bayesblend raises nothing: it stores the failed `OptimizeResult` and hands back whatever vector SLSQP stopped at, finite, non-negative and summing to 1, so no check on the weights themselves can see it. At this boundary that vector is the uniform starting point, because SLSQP stops at iteration 1; a solve that ran out of iterations hands back a partly fitted vector instead (measured with `maxiter=1` on a three-member problem: `res.x` is not `x0`). One shared cell below the boundary among those sixteen cells turned a 1.0/0.0 fit into 0.5/0.5, which scores 10.3 nats below the corner the fit should have found and is not the optimum of anything. So bayesblend is fed each cell's ELPD relative to that cell's best FINITE member and then floored at `LPD_FLOOR = -700` (which has to stay above -708.40, the log of the smallest normal double), in that order: flooring first ranks a member that gave zero density above a finite member further back. `_fit_weights` refuses `model_info.success is False` by name. A common per-cell offset cannot move the optimum, so the relative scale changes no correct answer.
* **An optimizer tolerance on a likelihood is RELATIVE or it is a lottery** (fixed 2026-07-27, `gallery/statistical/clark`). Our objectives are deviances over loss *amounts*, so their magnitude is the data's - Clark's concentrated Poisson deviance is ~-4.3e8 on genins, where one ULP is 6e-8. Its `fatol=1e-10` therefore demanded agreement ~600 million times finer than adjacent float64s, and scipy's Nelder-Mead stops only when the simplex spread <= `xatol` AND `max|f_i - f_0| <= fatol`, so that criterion could be met ONLY by every vertex evaluating bit-identically (measured: final f-spread exactly 0.0). It usually was, by luck - until the `pytest (all)` CI leg, whose torch+jax+pymc install changes BLAS/OMP thread counts and hence the summation order inside the objective, stalled a fit that had converged in 90 of 2000 iterations into a spurious `RuntimeError`. Use `fatol = rel * |f(x0)|`; keep absolute tolerances only for parameters that are O(1) by construction (log-space `xatol` here, which is what actually pins the fit). **Rescaling the objective is not an alternative** - the resolution floor comes from summing 1e8-magnitude terms, so subtracting `f(x0)` afterwards moves the value without buying back a bit. And **`res.success` is not the only convergence gate**: Nelder-Mead reporting `maxiter` with a collapsed simplex is exactly this failure, so honor `res.success` when it comes (its criteria are strictly tighter) and fall back to judging the simplex directly in the `maxiter` case. **A collapsed simplex is only converged if the OBJECTIVE collapsed too.** Coordinate spread alone accepts the opposite failure: the shrink steps contract to a point against the infeasibility plateau, where the objective is flat because every move is *rejected* - the optimizer giving up, not finishing. So require the coordinate spread <= 1e-6 AND the vertex-objective spread <= 1e3 x the fatol that magnitude warrants (1e-9 relative), AND every vertex finite and off the rejection sentinel. Check every vertex, not `res.fun`: `res.fun` is the BEST vertex, so a simplex straddling the feasibility boundary - objectives [1e11, 1e12, 1e12], two of them exactly on the sentinel - reads as healthy through it, and a coordinates-only gate accepted precisely that (caught in review of PR #55, before merge).
* **Segment columns are non-null, and the transforms depend on it** (fixed 2026-07-26; the bug predated milestone 6). Every join in `triangle/transforms.py` is a plain equi-join on `[*segments, field, origin_period, ...]`, and SQL join equality is false for NULL = NULL - so one null segment value silently deleted a whole cohort: `as_of`/`latest_diagonal` dropped it entirely, `to_incremental` kept only its first-dev cells and dropped the rest, and `validate(strict=False)` returned `[]` throughout. Identical on both backends. `io.from_long` now refuses null segments at ingestion and `validate.null_segments` flags a triangle built directly from an expression. Rejecting beat null-safe joins: a null segment key names no cohort, and four joins across two backends would have had to be made null-safe to buy support for a cohort nobody can identify. Reachable from the mart, not just hand-built frames - the data model's `dim_company` derives `company_name` (one of the three segments) via LEFT JOIN onto `sat_company_details`. Guard the empty-table boundary if you touch this: per-column `sum()` over zero rows is SQL NULL on duckdb and NaN on polars, so count rows first.
